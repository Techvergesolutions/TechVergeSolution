# TechVerge Sanity Studio

Sanity Studio for blog posts, services, authors and categories. Not part of the Vite build.
The website reads published service documents for its service listings and detail pages.
Blog content continues to use the existing blog queries.

## Setup

```bash
cd sanity
npm install
npm run dev
```

Studio runs separately (default port 3333). Sign in with a Sanity account that has access to project `xo7s2xmj`.

## Document type: `post`

| Field | Type | Required |
| --- | --- | --- |
| `title` | string | yes |
| `slug` | slug | yes |
| `excerpt` | text | yes |
| `description` | text | SEO meta |
| `publishedAt` | datetime | yes |
| `updatedAt` | datetime | optional editorial update date |
| `mainImage` | image + `alt` | recommended |
| `author` | reference to author | optional |
| `categories` | references to categories | optional |
| `relatedService` | reference to service | optional |
| `relatedPosts` | references to posts | optional; maximum three |
| `readingTimeMinutes` | number | optional |
| `tags` | string[] | optional |
| `body` | block content + inline images | yes for CMS articles |
| `faqs` | `{ question, answer }[]` | optional |
| `seo` | shared SEO object | optional |

Services have optional title, slug, short description, hero heading, Portable Text body,
features or process steps, FAQs, SEO settings, display order and related posts. The shared
SEO object provides title, description, social image, canonical URL and no-index overrides.
All new fields are optional so existing posts remain valid. The reusable typed GROQ queries
are in `src/lib/sanity/queries.ts`.

`content/services.ndjson` contains the initial six service documents as an import backup.
The existing documents have already been imported; check for matching slugs before importing
again, since duplicate document IDs and duplicate slugs are separate concerns. Initial HTML
metadata is generated at build time. The sitemap and RSS feed are generated by Vercel Functions
from published Sanity content and do not require a rebuild.

## Live content and webhook

The Vite application uses Sanity's listener to refresh active browser queries; it also polls
every 30 seconds as a fallback. `/sitemap.xml` and `/feed.xml` use a tagged Vercel Runtime
Cache snapshot. A valid webhook expires the relevant tag. Runtime Cache usage is billed by
Vercel. Blog article requests fetch published metadata directly from Sanity on every request,
so new or edited posts have their own initial HTML without a rebuild. Other static page and
service metadata is still generated at build time.

1. Generate a random secret locally, for example `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`.
2. Set `SANITY_WEBHOOK_SECRET` to that value in Vercel for the environment being deployed.
   Set `NEXT_PUBLIC_SITE_URL`, `VITE_SANITY_PROJECT_ID`, and `VITE_SANITY_DATASET` there too.
   For a private dataset, provide a server-only Viewer token as `SANITY_API_READ_TOKEN`.
3. Deploy the updated application. In the Sanity project's **API → Webhooks** settings, create
   a GROQ-powered webhook using URL `https://www.techvergesolution.com/api/revalidate` (replace
   the domain if `NEXT_PUBLIC_SITE_URL` differs), dataset `production`, and method `POST`.
4. Enable create, update, and delete events; disable draft and version document delivery.
   Set the filter to:

   ```groq
   coalesce(after()._type, before()._type) in ["post", "service", "page", "marketPage"]
   ```

   Set the projection to:

   ```groq
   {"_id": coalesce(after()._id, before()._id), "_type": coalesce(after()._type, before()._type)}
   ```

5. Enter the same secret in the webhook's **Secret** field, save it, then publish a test change.
   Check the webhook delivery log for HTTP 200 and verify the sitemap or feed. A 401 means the
   signature or secret did not match; a 503 means configuration or cache invalidation failed.

For automatic article links, select a post's **Related service**, **Categories**, and
optional **Related posts** in Studio. Related posts are shown in the chosen order, then
filled with posts in the same categories and recent posts. Service pages also show posts
that point to that service, together with any articles selected on the service itself.
The homepage shows the five most recent published Sanity posts. Articles with no recorded
service relationship do not display a related-service card.

## Market and contact content

Create one **Contact settings** document and publish the real email, WhatsApp number
(including country code), booking URL, and each actual hours/timezone pair. For example,
enter `Mon-Fri, 9am-6pm` and `GMT` as separate values. Enter other timezones only when
their hours are accurate; the site does not convert them or assume fixed offsets.

Create a **Market landing page** only for distinct, useful content. Enter its title,
slug, summary, unique body, optional SEO fields, and only authentic testimonials.
Published pages with content appear under `/markets/<slug>`, in the footer and sitemap;
noindex pages remain accessible but are omitted from the footer and sitemap. Add an
**Industries** item to a service and optionally select a relevant market page to link it.
After updating the webhook filter above to include `marketPage`, publish a test change.

## Hosted Studio (write posts from phone / any device)

After a **one-time** CLI login and deploy, you use the Studio in the browser — no laptop or `npm run dev` needed for day-to-day editing.

**Expected URL (after deploy):** [https://techverge-blog.sanity.studio](https://techverge-blog.sanity.studio)

### One-time setup (on your computer)

```bash
cd sanity
npm install
npx sanity login
npm run deploy
```

1. **`sanity login`** — browser opens; sign in with the same Sanity account that can access project `xo7s2xmj`. This stores credentials on your machine for **deploy only**. You do not run this every time you write a post.
2. **`npm run deploy`** — builds and uploads Studio to Sanity hosting. The CLI prints the final URL (should match `techverge-blog.sanity.studio`).

### Writing posts after deploy

1. Open **https://techverge-blog.sanity.studio** on phone or desktop.
2. Sign in with your **Sanity account** in the browser (normal website login).
3. Create/edit **Post** documents and **Publish**.
4. The live site reads **published** documents from the same `production` dataset (CDN, no browser token).
5. **Static HTML / sitemap update after a Vercel rebuild** — configure the publish webhook (see [`docs/SEO-SANITY-WEBHOOK.md`](../docs/SEO-SANITY-WEBHOOK.md)). Until rebuild finishes, a brand-new slug may 404 at the edge.

Local dev Studio (`npm run dev`, port 3333) is optional and only for testing schema/UI changes.

### Env notes

- Client: `VITE_SANITY_PROJECT_ID`, `VITE_SANITY_DATASET`, `VITE_SANITY_API_VERSION` only.
- Do **not** use `VITE_SANITY_TOKEN` (leaks into the JS bundle). Rotate any token that was ever committed or shared.
- Optional build-only: `SANITY_API_READ_TOKEN` for private datasets.
- CORS: allow `https://www.techvergesolution.com` and local Vite origins (see `docs/SEO-SANITY-WEBHOOK.md`).
